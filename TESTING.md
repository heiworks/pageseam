# PageSeam test guide

English | [简体中文](TESTING.zh-CN.md)

For anyone running regressions after changing PageSeam or the Dify plugin, and anyone evaluating parsing quality. There are five levels, from fast to slow: the first three run with one command, the last two need a human.

| Level | What it tests | How to run | Time | Pass criteria |
|-------|---------------|------------|------|---------------|
| 1. Unit tests | Cross-page table merging rules, headers and footers, image → PDF, Dify plugin chunking | `run-tests.sh unit` | 1 min | All pass |
| 2. End-to-end checks | 10-page mixed sample, cross-page tables, doc / docx, all three outputs | `run-tests.sh e2e` | 5 min | All pass |
| 3. Table cell evaluation | Cell accuracy of scanned tables at different skew angles | `run-tests.sh tables` | 4 min (full: 15 min) | Not below the current baseline (see below) |
| 4. Manual review | Convert files on the upload page; a person checks Word, PDF and Markdown | Browser | Depends on file count | See the checklist |
| 5. Knowledge base Q&A | Whether answers are correct once the results are in a knowledge base | Dify / WeKnora | Depends on question count | All of your own questions answered correctly |

Finish with your own real files (see "Evaluating with your own files"): the samples are generated and can't cover everything real scans throw at you.

## Setup

- Docker; build the image first: `docker build -t pageseam .` (dependencies and OCR models are inside the image).
- python3: runs the Dify plugin unit tests, standard library only.

## 1–3. Automated tests

```bash
./scripts/run-tests.sh                 # unit tests + end-to-end checks + table evaluation (quick)
./scripts/run-tests.sh unit            # one level only: unit / e2e / tables, can be combined
./scripts/run-tests.sh tables --full   # full table evaluation: 5 tables × 10 angles × PDF / JPEG
./scripts/run-tests.sh --deployed      # test the code in the image (default: your working tree)
```

The script copies `docparser/` and `tests/` from your working tree into a temporary container, runs it, then removes the container. **By default it tests the code in your working tree**, so you don't need to rebuild the image after changing code; add `--deployed` to accept the version inside the image.

Output for each level: one line per check starting with `✅` / `❌`; failures print expected and actual values. The last line is "全部通过" (all passed) or the levels that failed.

### Test files

| File | Contents |
|------|----------|
| [`tests/test_tables.py`](tests/test_tables.py) | Cross-page table merging: repeated headers, continuation without header, mixed scanned and text pages, no merge when column counts differ, rows split by page breaks, wrapped cells, page-number lines removed; merged cells expanded and two-row headers on text pages |
| [`tests/test_text.py`](tests/test_text.py) | Text page cleanup: headers and footers repeated on every page removed (even with different page numbers), while body text, headings, tables and a per-page "subtotal" with different numbers are kept; a header between parts of a cross-page table doesn't break merging; radical code points (⻋, ⽤) and compatibility ideographs (U+F9DB 率) mapped back to common characters; docx default East Asian language switched to the body text's language |
| [`tests/test_i18n.py`](tests/test_i18n.py) | English / Chinese messages: `Accept-Language` negotiation (q values, unsupported languages, default), every message formats in both languages with the same parameters |
| [`tests/test_images.py`](tests/test_images.py) | Image → PDF: recognized at native pixel size without upscaling, oversized images downscaled, webp, multi-page TIFF, phone photo EXIF orientation, transparent backgrounds |
| [`tests/test_jobs.py`](tests/test_jobs.py) | Job status: a job that finishes while a status request is reading its progress stays succeeded / failed instead of going back to running; a status request returns a consistent snapshot that later changes don't affect; queued → running → succeeded; other API keys can't see the job |
| [`dify-plugin/tests/test_chunking.py`](dify-plugin/tests/test_chunking.py) | Plugin chunking: maximum chunk length and maximum table length, cross-page tables as their own chunk, long tables split by rows with headers |
| [`tests/check_pipeline.py`](tests/check_pipeline.py) | 10-page mixed sample (generated by [`make_sample.py`](tests/make_sample.py)): classification, searchable PDF identical pixel by pixel and searchable, Word, Markdown |
| [`tests/check_tables.py`](tests/check_tables.py) | Cross-page table and Word samples (generated by [`make_tables_sample.py`](tests/make_tables_sample.py)): merged row counts, doc / docx conversion, recognition of embedded scans, table merging in Word output |
| [`tests/eval_tables.py`](tests/eval_tables.py) | Scanned table cell evaluation, see below |

## 3. Table cell evaluation

Checking only whether key fields are present can't catch "all values recognized, but in the wrong column". This level renders tables with known content as scans (grayscale, noise), skews them at different angles, recognizes them both as scanned PDF pages and as JPEG images, expands merged cells and compares cell by cell, by (row, column), against the ground truth. Whitespace and full-width / half-width differences are ignored.

| Table | Characteristics |
|-------|-----------------|
| Delivery plan | Landscape page, 6 columns, many dates |
| Equipment purchase | Total row spanning 5 columns (merged cell) |
| Technical parameters | Many "—" placeholders, special symbols (±, μm, m³) |
| Acceptance record | 21 rows, symbols such as ℃ and ≤ |
| Bill of materials | 21 rows × 6 columns, mostly numbers |

Angles: 0, ±0.3°, ±0.6°, ±1°, ±2°, 3° (full); 0, ±1°, 3° (quick, PDF only).

One line per case: `table path angle correct/total time deskew-angle first-error`, then cell accuracy and the number of fully correct tables per angle. `--min 0.8` fails the run if any table is below 80% (to catch severe problems such as a whole table shifted).

### Current baseline (full evaluation, 8-core CPU)

| Version | Cell accuracy | Fully correct tables | Per page |
|---------|---------------|----------------------|----------|
| Before deskew | 0.490 | 9 / 100 | 11.0 s |
| With deskew | 0.912 | 21 / 100 | 11.0 s |
| Plus native-resolution images and separate recognition of split cells | 0.963 | 28 / 100 | 8.7 s |
| **Current** (plus "—" placeholders and separate recognition of single-line cells) | **0.984** | **51 / 100** | **8.6 s** |

After changing OCR-related code, run the full evaluation; accuracy must not drop below the current baseline. If it improves, update this table.

Remaining errors are mostly:
- **Merged cells**: the total row of the equipment purchase table (spanning 5 columns) gets the wrong structure, the table refill is skipped, and single digits in that table can be missed.
- **Single characters**: "X" read as "×", "℃" as "℃C", "1" as "7" — errors of the OCR model itself.

## 4. Manual review (upload page)

Automated tests can't see layout; Word and searchable PDF need a human eye.

```bash
docker compose up -d     # see "Quick start" in the README
```

Open `http://localhost:8000/` in a browser, enter the API key (stored only in this browser), tick all three outputs, choose automatic OCR, convert, then download the results and compare them with the original. Samples can be generated with `tests/make_sample.py` and `tests/make_tables_sample.py`.

Checklist:

| Output | What to check |
|--------|---------------|
| Markdown | Typos or missing characters on scanned pages (amounts, dates, account numbers, symbols like ‰); cross-page tables merged into one (preceded by `<!-- table pages a-b -->`), header appearing once, first and last rows present; every value in the correct column; no paragraphs containing only a page number |
| Word | With "match original pagination", one table per page; with "merge into one table", a single table for each cross-page table, with "Repeat as header row at the top of each page" ticked in table properties; landscape pages stay landscape |
| Searchable PDF | Looks identical to the original; Ctrl+F finds text on scanned pages, and the highlight when selecting text lines up with the characters in the image (also on skewed scans) |

## 5. Knowledge base Q&A

The results end up in a knowledge base, so the final check is whether retrieval and Q&A get the answers right:

- **Dify**: install the [Dify plugin](dify-plugin/GUIDE.md), connect the `chunks` output of "Parse document to Markdown" to the "Knowledge Base" node in a knowledge pipeline, import the samples and ask a few questions.
- **WeKnora**: integrate following [integrations/weknora](integrations/weknora/README.md) and choose mineru in the knowledge base's parser rules.

Cover every capability in your questions: numbers on scanned pages, the last row of a cross-page table, a continuation table without a header, text inside a screenshot on a page. When an answer is wrong, first check whether the parsing result (Markdown) contains the correct content: if it does, the problem is retrieval or chunking; only if it doesn't is it a parsing problem.

## Evaluating with your own files

Generated samples are "clean". Common in real files but not covered by the samples: perspective distortion and shadows in phone photos, stamps over text, greyish photocopies, handwritten notes, tables without ruling lines, lots of merged cells.

1. Put files in `tests/samples/` (git-ignored, never committed). Redact sensitive information first.
2. Convert them on the upload page and go through the manual review checklist.
3. To check retrieval, import the files into a knowledge base as in level 5 and ask a few questions of your own.
4. Record the results (the format below is suggested) and open a GitHub issue for problems.

```markdown
| File | Pages | Type | Time | Problem (page, symptom) |
|------|-------|------|------|-------------------------|
| contract.pdf | 12 | Scan with stamps | 70 s | Page 5: "Unit price" and "Amount" columns mixed up |
```

### Opening an issue

Describe the symptom clearly in the title. In the body include: file type and characteristics (scan / text, skew, stamps…), page numbers, expected result, actual result (paste a Markdown excerpt), and whether it reproduces with a generated sample. Don't attach files with sensitive information — describe their characteristics instead; ideally build a reproduction with the functions in `tests/make_sample.py` and add it to the evaluation set.

## Regression after code changes

| What changed | Run at least |
|--------------|--------------|
| `markdown.py`, `word.py` | `run-tests.sh unit e2e` |
| `ocr.py`, `classify.py`, `convert.py` | `run-tests.sh` + `run-tests.sh tables --full`, compare with the baseline |
| Dify plugin | Plugin unit tests + level 5 |
| Dependencies (`requirements.txt`, upgrades) | `scripts/update-constraints.sh`, rebuild the image, then `run-tests.sh` + `run-tests.sh tables --full` |
| Before a release | All five levels; after building the image, run `run-tests.sh --deployed` once more; `scripts/security-check.sh --image pageseam` (secrets, dependency vulnerabilities, code, Dockerfile, image vulnerabilities). It can also be run manually in GitHub Actions ("Security check") |
